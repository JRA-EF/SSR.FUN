# Security Invariants

## Core invariants (mission-mandated, verbatim intent)

1. **Reserve Tokens cannot mint without backing.** `mint_reserve_tokens_in_kind` transfers every required asset amount into the Reserve's vaults via CPI *before* the mint CPI executes, in the same instruction -- if any transfer fails, the whole instruction reverts atomically and no tokens are minted. `seed_reserve` additionally reloads each vault post-transfer and requires a nonzero balance before minting the initial supply (mirroring the reference protocol's own `initialize()` assertion). ⏳ PLANNED (needs a mock "transfer succeeds but under-delivers" adversarial test once Token-2022 test mints are available).
2. **Reserve Token mint authority is controlled only by the program-derived authority.** `mint_authority` is a PDA (`["mint_authority", reserve]`) with no corresponding keypair; the mint's `mint::authority` is set to this PDA at `create_reserve` and never reassignable by any instruction. ✅ verified by construction (no `set_mint_authority`-equivalent instruction exists in the instruction set).
3. **Redemption cannot return more than proportional ownership.** `redeem_reserve_tokens_in_kind` computes entitlement via floor-rounded `mul_div_floor(net_shares, vault_balance_before, total_supply_before)` -- structurally cannot exceed the redeemer's proportional share of what existed before their own burn. ⏳ PLANNED (extreme-decimal-sweep test, see TEST_PLAN.md).
4. **Vault assets cannot leave through an unauthorized instruction.** Only two instructions ever move vault assets: `mint_reserve_tokens_in_kind`/`seed_reserve` (in) and `redeem_reserve_tokens_in_kind` (out). No instruction gives any signer (root manager, delegate, or `ProtocolConfig` authority) a direct "withdraw" path. ✅ verified by construction -- see the full instruction list in INSTRUCTION_REFERENCE.md; none is a bare withdrawal.
5. **One Reserve cannot access another Reserve's vaults.** Every vault's address AND its owning `vault_authority` PDA are derived from that specific Reserve's own pubkey (`["reserve_vault"/"vault_authority", reserve, ...]`). `instructions/common.rs::load_asset_legs` independently re-derives and checks the expected vault PDA for the Reserve in the current instruction's context against whatever account was actually supplied -- passing another Reserve's vault fails this check before any transfer CPI runs. ✅ TESTED (`tests/ssr_protocol.ts` "cross-Reserve isolation" test now fully implemented: creates two real Reserves, then attempts `mint_reserve_tokens_in_kind` on Reserve One while substituting Reserve Two's `reserve_asset`/`vault` for the same underlying asset mint, asserting the call throws. Typechecks; **not yet executed** -- see TEST_PLAN.md).
6. **Reserve Token supply remains backed by Reserve Vault balances.** Follows from invariants 1+3: the only two supply-changing paths always move a proportional, atomically-computed asset amount alongside the exact supply change. ⏳ PLANNED (property-style test: sequence of mints/redeems/fee accruals, assert vault-value-per-share never decreases outside of documented fee mechanics).
7. **Duplicate Reserve Assets are prohibited.** `initialize_reserve_asset`'s `reserve_asset` account uses `init` at a PDA seeded by `(reserve, asset_mint)` -- attempting to register the same mint twice fails with an account-already-in-use error from Anchor's `init` constraint itself. ✅ TESTED (`tests/ssr_protocol.ts` "rejects registering a duplicate asset mint").
8. **Target allocations cannot exceed the defined total.** `initialize_reserve_asset` and `update_targets` both check the running/new sum against `BPS_DENOMINATOR` (10,000) before writing. ✅ TESTED (happy-path test asserts the two registered assets sum to exactly 10,000; `⏳ PLANNED` explicit over-100% rejection test).
9. **Integer rounding cannot systematically enrich a privileged party at holders' collective expense** -- rounding is deliberately protocol-favoring (ceiling on mint requirements/fees, floor on redemption payouts), never favoring an individual privileged account over the pooled remaining-holder set. The redemption-fee "retained backing" mechanism (see `redeem_reserve_tokens_in_kind.rs`) explicitly accrues to *all remaining holders proportionally*, not to any one address. ⏳ PLANNED.
10. **Residual dust remains bounded and documented.** Bounded by integer-division truncation only (at most `asset_count` wei-equivalent units lost per mint/redeem call); no separate dust ledger exists, matching the reference protocol's current (post-2.0.0) design. Not yet load-tested at extreme decimal combinations -- ⏳ PLANNED (Extreme-style sweep, see TEST_PLAN.md).
11. **Paused operations fail safely.** `Reserve.status == Paused` blocks `mint_reserve_tokens_in_kind`, `update_targets`, `pause_reserve` (already paused), and any instruction requiring `Active` status; `redeem_reserve_tokens_in_kind` explicitly does NOT check pause state at all (see DEC-0016). ✅ TESTED (pause/unpause happy path); ⏳ PLANNED (assert redeem still works while paused -- not yet in the test file).
12. **Invalid signers fail.** Every mutating instruction either has an Anchor `has_one`/explicit key-equality check against `Reserve.manager`, or routes through `require_reserve_permission` (manager-or-permitted-delegate). ✅ TESTED (unauthorized-pause-attempt test).
13. **Delegates cannot exceed their permissions.** `require_reserve_permission` checks a specific bit of `Delegate.permissions`; reserved bits 10-15 are rejected at `add_delegate`/`update_delegate_permissions` time (`ReservedPermissionBitSet`) so no future flag can be silently pre-granted by stale-encoded old data. ✅ TESTED (delegate-scope-boundary test: can update targets, cannot pause).
14. **Root authority transitions are explicit.** `transfer_reserve_manager` is the only instruction that changes `Reserve.manager`, gated to the current manager only, emitting `ReserveManagerTransferred`. ⏳ PLANNED (no test yet).
15. **Account substitutions fail.** Every PDA-derived account (`reserve_asset`, `vault`, `vault_authority`, `mint_authority`, `reserve_token_mint`, `delegate`) is checked via Anchor `seeds =`/`address =` constraints, re-deriving the expected address rather than trusting whatever was supplied. ✅ verified by construction across every instruction file; cross-Reserve case specifically ⏳ PLANNED per invariant 5.
16. **Repeated initialization fails.** Every `init`-constrained account (`ProtocolConfig`, `Reserve`, `ReserveAsset`, `Delegate`, the Reserve Token mint) fails at the Anchor/System-Program level if the target PDA already has data -- calling e.g. `create_reserve` twice for the same `reserve_id` is structurally impossible since `reserve_id` only ever advances forward via `ProtocolConfig.reserve_count`. ⏳ PLANNED (explicit re-init test).
17. **Partial multi-step flows cannot produce unbacked tokens.** `Reserve.status` gates this precisely: `mint_reserve_tokens_in_kind` and `redeem_reserve_tokens_in_kind` both require `Active` (or `Paused`, for redeem), which is only reachable after `seed_reserve` succeeds -- a Reserve stuck at `Created`/`AssetsInitializing` (abandoned mid-creation) cannot mint or be redeemed from at all. ✅ TESTED (rejects-seeding-an-already-Active-Reserve test covers the adjacent case; explicit "mint on a never-seeded Reserve fails" ⏳ PLANNED).
18. **Fees cannot make the Reserve insolvent.** Mint fee is deducted from newly-minted shares (never reduces existing backing); TVL fee dilutes supply proportionally to all holders equally rather than pulling assets out of vaults; redemption fee retains backing in the vault rather than removing it. No fee mechanism transfers vault assets to a fee recipient directly -- only ever mints new Reserve Tokens (a dilution, never a vault drain). ⏳ PLANNED.
19. **Unsupported token behavior fails safely.** `validate_asset_mint_extensions` (`instructions/common.rs`) rejects Token-2022 mints carrying `TransferFeeConfig`, `TransferHook`, `PermanentDelegate`, `NonTransferable`, or `ConfidentialTransferMint` at `initialize_reserve_asset` time -- see the "Weird ERC20s"-style table below. **UNVERIFIED**: this code was written without a compiler; the exact `spl_token_2022::extension::ExtensionType` variant names must be checked against the installed crate version once a toolchain exists (flagged in the code itself).

## Supported / rejected token behavior (SSR's "Weird Tokens" matrix)

Directly modeled on the reference protocol's own documented support matrix (RESERVE_REFERENCE_ANALYSIS.md section 15).

| Behavior | Supported? | Why |
|---|---|---|
| Classic SPL Token, any decimals | Yes | Baseline case, no extension data to inspect. |
| Token-2022, no extensions | Yes | Behaves identically to classic SPL Token for `transfer_checked` accounting purposes. |
| Token-2022 `TransferFeeConfig` | **No** | Actual amount received by the vault would differ from the requested amount -- silent under-collateralization. |
| Token-2022 `TransferHook` | **No** | Arbitrary third-party program logic could alter transfer behavior/side-effects unpredictably. |
| Token-2022 `PermanentDelegate` | **No** | Would let an address other than this program move vault tokens -- directly violates "no operator withdrawal powers over Reserve Assets." |
| Token-2022 `NonTransferable` | **No** | Vault could never move the asset back out -- breaks redemption entirely. |
| Token-2022 `ConfidentialTransferMint` | **No** | Balances aren't plainly readable -- breaks the balance-delta accounting this program relies on throughout. |
| Token-2022 `InterestBearingConfig` | Not yet evaluated | Likely safe (interest accrual is a display/rate concept, not a transfer-time side effect) but not explicitly allow-listed or tested -- treat as unsupported until confirmed. |
| Upward/downward rebasing tokens (classic SPL, non-standard) | Not evaluated | The reference protocol flags rebasing tokens as a caveat even where "supported" (balance-delta accounting can misattribute a rebase event as a trade). SSR inherits the same caveat conceptually; no rebasing-token test exists yet. |
| Fee-on-transfer via a non-Token-2022 mechanism | Not applicable | Classic SPL Token has no such mechanism; only Token-2022 extensions can express this. |

## Reserve-creation partial/abandoned-state handling

A Reserve stuck between `Created` and `Seeded` (creator registered some assets then walked away) is:
- **Visible on-chain** via `Reserve.status` -- not ambiguous.
- **Not mintable/redeemable** -- both instructions require `Active`.
- **Not currently closeable/reclaimable.** There is no `close_abandoned_reserve` instruction in v1 -- the creator's rent for the `Reserve`/`ReserveAsset`/vault accounts stays locked indefinitely if they abandon creation. This is an accepted, documented v1 limitation (rent cost, not a security hole), **not** a mission requirement violation (the mission says an abandoned Reserve should have defined behavior, which "permanently visible as incomplete, non-functional" satisfies) -- but is worth revisiting: ⏳ candidate future instruction, not built in v1.

## Upgrade / admin blast-radius summary

See docs/protocol/SSR_ARCHITECTURE.md section 7 for the full authority-boundary table. Restated as a security invariant: **compromise of the SSR frontend, website, API, indexer, treasury, or `ProtocolConfig` authority cannot withdraw a single token from any already-created Reserve's vaults.** The only two paths that ever move vault assets require either a depositor's own signature (mint) or a redeemer's own signature plus their own token burn (redeem) -- no administrative signer appears in either CPI's authority chain except the two Reserve-scoped, non-keypair PDAs (`mint_authority`, `vault_authority`), which are only ever invoked by this program's own instruction logic, never independently.
